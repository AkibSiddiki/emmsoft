How eMythMakers Powers 120M+ Digital Readers with Zero Crashes: Multi-Tier Reverse Proxy & Concurrency Architecture

Nurul Afsar Polash

Chief Technology Officer & Systems Architect

LinkedIn

When national elections or catastrophic breaking news occurs in South Asia, digital media traffic does not ramp up smoothly—it hits like a tsunami. Standard monolithic setups crash when simultaneous requests spike from 2,000 to 60,000 in under 90 seconds. Here is the unvarnished engineering blueprint of how eMythMakers keeps Bangladesh's largest media portals responsive with sub-50ms TTFB.

1. The Problem: The Anatomy of a Breaking News Collapse

Most publishing platforms fail not because the server CPU lacks raw power, but because of database connection pool exhaustion. In traditional architectures (WordPress, standard monolithic PHP/Node apps), every visitor request triggers database queries: session validation, taxonomy checks, related article queries, and user cookie evaluation.

Under normal traffic of 1,500 readers, MySQL handles 300 queries per second effortlessly. But when breaking news alerts blast out to millions on social media:

  • Connection pools fill within 3 seconds, reaching the max connection ceiling (e.g. 500 max connections).
  • Subsequent PHP-FPM worker threads queue up waiting for an open database slot.
  • Worker threads consume server RAM while idle, triggering the Linux kernel Out-Of-Memory (OOM) killer.
  • Nginx returns HTTP 502 Bad Gateway or HTTP 504 Gateway Timeout.

2. Varnish 7 VCL: Serving 98.4% of Traffic Directly from RAM

Our first line of defense is a custom-compiled Varnish 7 reverse-proxy caching layer deployed on dual dedicated bare-metal nodes. By configuring granular cache key hashing, we strip non-essential analytical cookies (e.g. Google Analytics, Facebook Pixel) at the edge before evaluating the cache hash.

Below is a sanitized snippet of our production Varnish VCL configuration implemented across major tier-1 media deployments:

/etc/varnish/default.vcl — Concurrency Caching Rules 
vcl 4.1;

# Define High-Speed Editorial Upstream
backend default {
    .host = "10.0.1.10";
    .port = "8080";
    .probe = {
        .url = "/healthz";
        .interval = 3s;
        .timeout = 1s;
        .window = 5;
        .threshold = 3;
    }
}

sub vcl_recv {
    # Bypass caching strictly for authenticated newsroom editors
    if (req.http.Cookie ~ "emm_editorial_session") {
        return (pass);
    }

    # Strip client tracking cookies to ensure universal cache hit
    set req.http.Cookie = regsuball(req.http.Cookie, "(^|; ) *__utm[^;]+;? *", "");
    set req.http.Cookie = regsuball(req.http.Cookie, "(^|; ) *_ga[^;]+;? *", "");

    # Activate 6-hour Grace Mode for stale-while-revalidate safety
    set req.grace = 6h;
    return (hash);
}

sub vcl_backend_response {
    # Cache public news articles for 10 minutes with instant purge API
    if (beresp.status == 200) {
        set beresp.ttl = 10m;
        set beresp.grace = 6h;
    }
}

4. Five Non-Negotiable Rules for Concurrency Engineering

Through 15 years of engineering high-traffic media and enterprise platforms in Dhaka, our team has distilled five core rules that every architect should adhere to:

  1. Never let unauthenticated readers touch the database: If an article is publicly readable, it must be served from memory or edge proxy. Period.
  2. Implement Grace Mode on all reverse proxies: If the database freezes or an upstream worker crashes, Varnish must serve the last known good copy of the page rather than showing an error screen.
  3. Decouple session state into Redis clusters: Application workers must remain entirely stateless so instances can be scaled horizontally without dropping user authentication.
  4. Sanitize and normalize tracking cookies at the edge: Client-side analytics cookies that differ per visitor will destroy cache hit rates if not stripped before cache key hashing.
  5. Test under synthetic chaos: Run load simulations that purposely kill application nodes during peak traffic. If the user notices a single glitch, your failover is incomplete.
